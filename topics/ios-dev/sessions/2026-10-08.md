- Began with two records previously persisted through explicit saves.
- Removed the explicit-save blocks, inserted one new Milk and one new Eggs,
  backgrounded the app, stopped it, and relaunched.
- Learner-reported results progressed from two records to four records, with all
  four present after relaunch. This demonstrates that the new records reached the
  persistent store without an explicit `save()` call during that run.
- The prediction incorrectly combined matching names into two records with summed

  creates a new record rather than finding and updating one with the same name.

  wording about saving “during relaunch” needed refinement. The run does not
  identify the exact save time or prove that backgrounding itself triggered it.

## Shopping persistence design probe

- Correctly mapped one item to `@Model`, UI records to `@Query`, mutations to
  `ModelContext`, persistent configuration to the model container, and validation
  to ordinary Swift logic.
- Correctly stated that `@Query` retrieves and observes rather than owns records,
  and predicted a name-sorted zero-to-two-to-three record sequence including a
  second Milk insertion.
- Correctly identified that bypassing existing validation could persist blank
  names, nonpositive quantities, and duplicates.
- Needed precision that `@Model` represents one persistable record rather than a
  query collection; the container configures the schema/backing store and supplies
  a context; and a recreated view can query current data because the persistent
  data stack outlives that view value.

## Persistent shopping Add implementation

- Converted `ShoppingItem` to an `@Model` final class and supplied a persistent
  two-model app container for `PantryItem` and `ShoppingItem`.
- Built `PersistentShoppingView` with an environment context, name-sorted query,
  view-local drafts/status, query-derived count/rows, and context insertion.
- Kept the validation in a separate method with the required empty-name,
  exact-duplicate, invalid/nonpositive-quantity, then success precedence.
- Cleared drafts only after success and preserved them on rejection. The
  learner's duplicate-precedence explanation was correct.
- The Preview used only `ShoppingItem` rather than both schema types; the required
  two-model in-memory container correction remains part of the next edit.
- The active app root uses the persistent query path. Older `ContentView` and
  `ShoppingList.list` declarations remain disconnected legacy code and are not
  evidence of a second active persistent source.

## Run evidence and persistence boundary

- Predictions and learner-reported actuals matched for fresh launch, successful
  Milk, rejected duplicate Milk with invalid quantity, rejected blank name, and
  successful Eggs. The query displayed both Milk and Eggs before termination.
- After backgrounding, stopping, and relaunching, only Milk remained. This is
  evidence that query visibility can include a pending context insertion that a
  later context cannot retrieve from the store.
- The learner suggested that termination occurred too quickly and that Milk had
  existed longer than Eggs. This is a plausible autosave-timing hypothesis. With
  guidance, the evidence was classified more narrowly: Milk reached the store;
  Eggs did not; the precise autosave moment remains unknown.
- The learner explicitly identified punctuation and dash-style feedback as
  irrelevant to the persistence target. The tutor agreed to assess such cosmetic
  differences proportionally unless exact presentation is itself the requirement.
