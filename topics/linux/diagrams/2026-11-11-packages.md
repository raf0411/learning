# Packages and catalogs — 2026-11-11

```text
Software package
  |-- files: programs, libraries, documentation, ...
  `-- metadata: name, version, dependencies, ...

Remote repository
        |
        | refresh package information (apt update)
        v
Local APT catalog ------> candidate selection
                               |
                               | installation / upgrade
                               v
Installed files + local package records
```

Reading the saved catalog does not refresh it. A repository URL in output is
the source of catalog information, not proof of live fetching.

| Question | Tool used |
| --- | --- |
| What would the shell run? | `command -v locate` |
| Which package records ownership of this path? | `dpkg-query -S /usr/bin/ls` |
| What metadata does an installed package have? | `dpkg-query -s coreutils-from-uutils` |
| What is installed and what would APT choose? | `apt-cache policy locate` |
| What packages match a search? | `apt-cache search '^locate$'` |
| What would an installation change? | `apt-get --simulate install locate` |

## Distinctions

- An alias is a shell definition, not an installed package record.
- A package search match does not prove installation.
- A catalog refresh can change Candidate without changing Installed.
- Simulation describes proposed changes without installing them.
- Package installation and creation/freshness of an application's data are
  separate questions. Installing locate does not by itself prove its search
  index is ready or current.

## Verified on this VM

- `/usr/bin/ls` is recorded under `coreutils-from-uutils`; use this observed
  result rather than assuming a generic package name.
- Its rust-coreutils and gnu-coreutils dependencies were both installed.
- locate changed from Installed (none) to 4.10.0-3build2 after installation.
- Shell lookup then returned `/usr/bin/locate`.
