## Testing a value that changes

- Quiz on which test catches the bug and still works on another machine: the learner chose the **hard-coded literal** `Disk /: 7.3G of 29G (28%)`. **Incorrect.**
  - The tutor taught that a literal causes false alarms as the disk fills or on the homelab. The fix is to work out the expected value at test time from an independent source.
- Expected-value command `df -h / | awk '{print $5}' | tail -n 1` → `28%`. **Independent.**
- Test case 6, written **without a model block**:
  ```bash
  expected=$(df -h / | awk '{print $5}' | tail -n 1)
  bin/sysprobe.sh samples/auth-mixed.log | grep 'Disk /:' | grep -q "$expected" >/dev/null 2>/dev/null
  ```
  It runs the program, narrows to the Disk line, uses the computed expected value and has correct `-eq 0` polarity. 6/6 PASS.
  - Minor, not raised: a substring match can give a false PASS (for example, `2%` matches `12%`), and the redirects apply to grep rather than to the script.
- Asked "how do you prove it can fail?", the learner **proposed a mutation test unprompted** ("change the disk ... to not include the 28%"). The tutor suggested reintroducing the real bug instead.

- **`which` versus `command -v`:** the learner asked. The tutor taught that `command -v` is a POSIX builtin, while `which` is an external program that varies between systems.

  - `command -v nosuchcmd` → no output, status 1.
