# Session — 2026-09-20

Status: ended at the learner's request after completing a load-average lab,
spaced memory review, and the first disk-space diagnosis sequence.

## Focus

Rebuild load average from CPU capacity, observe its smoothing on the two-CPU
Ubuntu desktop VM, separate runnable CPU demand from uninterruptible I/O wait,
retrieve swap and available-memory concepts, and begin filesystem capacity
diagnosis with `df`, `du`, and inode counts.

## Opening learning boundary

The learner said they had forgotten everything when presented with the pending
load 8.00 comparison. The prior record showed that load average had only been
introduced at the end of the previous session and the comparison had never
been attempted. The lesson therefore treated this as a retrieval failure at a
new learning edge rather than evidence that earlier skills were lost.

## Load average and CPU capacity

The CPU-only model began with logical CPUs as execution slots. After direct
teaching, the learner correctly answered that load 3.00 on two CPUs could mean
two tasks running and one waiting. They initially reversed the trend in both
`6.00 3.00 1.00` and `2.00 5.00 9.00`, reading the displayed order as a
chronological order. The repair rule was:

```text
label values left to right: 1, 5, 15 minutes
read the trend right to left: oldest to newest
```

They then correctly rewrote `1.50 3.00 6.00` as
`6.00 -> 3.00 -> 1.50`, identified falling demand, and selected the older
6.00 value as above four-CPU capacity.

The Linux caveat was added: load includes runnable tasks and tasks in
uninterruptible sleep, commonly I/O wait. Given high load, 75% CPU idle, and
many `D`-state tasks, the learner correctly chose I/O/storage as the first area
to investigate.

## Live Ubuntu VM observations

The VM reported two logical CPUs and an initially quiet load:

```text
$ nproc
2

$ uptime
load average: 0.00, 0.00, 0.00
```

A `top -b -n 1` snapshot reported one running task and 84% CPU idle while load
still displayed as zero. The learner correctly separated an immediate task
snapshot from a smoothed, rounded load value and rejected CPU saturation.

One bounded `yes` workload missed its active observation window and exited via
`timeout` with status 124. A timing-controlled retry used:

```bash
timeout 60s yes > /dev/null & sleep 20; uptime
```

It produced:

```text
load average: 0.29, 0.08, 0.04
```

The learner correctly reconstructed `0.04 -> 0.08 -> 0.29` and rising demand,
but did not initially know why the one-minute value had not jumped to 1.00.
Teaching connected the result to exponential smoothing; the simplified
one-minute response after 20 seconds is approximately 0.283. After the workload
expired, `uptime` reported `0.00, 0.07, 0.06`; the learner correctly explained
the near-zero rounding and persistence of longer-window history.

Both disposable workloads expired through `timeout`; no process cleanup is
required.

## Runnable versus blocked work

The learner ran `vmstat -y 1 4`. All four one-second rows showed `r=0`, `b=0`,
98–100% idle CPU, and `wa=0`. They initially could not interpret the fields
after their first introduction. After a direct table explanation, they
correctly diagnosed both unfamiliar rows:

```text
r=5 b=0 id=0  wa=0  -> CPU pressure and runnable backlog
r=0 b=4 id=80 wa=20 -> uninterruptible I/O pressure
```

They also correctly handled a combined high-load, high-idle, many-`D` scenario,
although the first wording overclaimed that no task could be waiting for CPU.
The repaired conclusion was that load alone cannot reveal the exact runnable
queue because it combines runnable and uninterruptible tasks.

## Spaced memory review

The same `vmstat` output showed `swpd=0`, `si=0`, and `so=0`. The learner
correctly recognized no swap-in or swap-out activity but initially described
whole tasks as moving and did not recall whether swap related to VIRT or RSS.
After repair, they correctly inferred from a fresh page-set transition that B
moved from RAM to swap, VIRT remained constant, and RSS decreased.

Given 512 MiB occupied swap, zero transfers for several minutes, and 3 GiB
available RAM, the learner correctly diagnosed no evidence of current memory
pressure. Teaching clarified that cold pages can remain in swap after earlier
pressure has ended.

For free versus available RAM, the learner again described applications as
borrowing from a separate `available` pool. A physical-RAM diagram repaired the
model. They correctly reconstructed available as an estimate based mainly on
unused RAM plus reclaimable occupied memory and rejected adding free,
buff/cache, and available because that would double-count RAM. These memory
skills remain GUIDED because the successful answers followed direct repair.

## Disk-space diagnosis

The opening probe produced Neofetch/Fastfetch as a possible disk overview but
no filesystem diagnostic commands. Teaching separated filesystem capacity
(`df`) from path-level accounting (`du`).

The live root-filesystem observation was:

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sda2      ext4   29G  6.3G   21G  24% /
```

The learner independently identified the backing device, filesystem type,
used and available capacity, and correctly rejected a nearly-full diagnosis.
`du -sh "$HOME"` reported 17 MiB; the learner correctly distinguished this
directory-tree total from the root filesystem's 6.3 GiB of total usage.
Breaking the home tree down showed `.cache` as the largest immediate child at
16 MiB, which they selected without confusing the 17 MiB parent total for a
child.

`df -i /` reported 10% inode use. The learner first attributed its difference
from the 24% block use to the `-hT` formatting options. Teaching established
that `-i` selects inode capacity, whereas `-h` changes formatting and `-T` adds
filesystem type. They then correctly diagnosed a hypothetical 100%-inode,
40%-block failure of `touch`.

For a failed write under `/var/log/myapp`, the learner correctly selected the
existing parent as the `df` target. Given 98% block use and 12% inode use, they
selected blocks as the scarce resource and independently adapted the earlier
command:

```bash
du -h --max-depth=1 /var/log/myapp | sort -h
```

The `-x` same-filesystem refinement was then introduced. The open-but-deleted
file explanation for a `df`/`du` discrepancy was introduced at session end,
but its understanding check was not attempted.
