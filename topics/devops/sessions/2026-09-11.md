## Concepts covered

- A `top` frame is the state sampled at one refresh instant, not the whole time
  interval until the next refresh.
- An already-running process can appear in the first frame. A process whose
  entire lifetime falls between two refreshes can be missed by both frames.
- Installed `top(1)` documentation defines task `%CPU` over the interval since
  the last screen update; procps-ng `ps` reports a lifetime average.
- CPU time divided by elapsed wall time gives a unitless utilization ratio;
  multiplying by 100 expresses it as a percentage.
- A socket is a physical CPU package, a core is a physical execution core, and
  a logical CPU is a hardware thread exposed to the operating system.
- `nproc` reports logical processing units available to the current process; it
  does not by itself reveal the number of physical cores.
- In `top` Irix mode, one fully busy logical CPU corresponds to about `100%`, so
  a multi-threaded process may exceed `100%`. In Solaris mode, that value is
  divided by the total visible logical CPUs so whole-machine capacity is `100%`.
- A PID-filtered `top` view reports zero tasks once the selected PID has exited.
- Changing from the 16-logical-CPU physical server to a two-logical-CPU VM
  changes the Solaris denominator: one fully busy logical CPU is about `50%`
  there, while the Irix-style value remains about `100%`.
- `VIRT` counts mapped or reserved virtual address ranges; it is not limited to
  installed physical RAM and does not shrink merely because a mapped page
  becomes resident.
- `RES`/RSS is the resident subset of those mappings. Paging a mapped page into
  RAM raises residency without removing it from `VIRT`; eviction lowers
  residency while preserving the mapping.
- `SHR` is a potentially shareable subset of `RES`, not extra memory to add to
  it. Summing per-process RSS can count the same shared physical pages more than
  once.

## Mistakes and corrections

- Initially treated the interval from `t=0` to `t=2` as a continuously observed
  `top` frame, so predicted that a process existing only between the refreshes
  would appear. Corrected after “frame” was defined as one sampled instant.
- Initially guessed that `ps` could not show a low value while `top` showed a
  high value for the same process. A numerical example established that their
  lifetime and recent windows can legitimately produce both values.
- Repeatedly changed the Irix scale: at different points treated one fully busy
  logical CPU as `200%`, three as `600%`, or four of sixteen as only `100%`.
  Corrected rule: one fully busy logical CPU is about `100%` in Irix mode.
- For the actual 16-logical-CPU server, first used `1/1` as the Solaris denominator
  and converted it to `0%`. Correct denominator is all 16 logical CPUs, so one
  fully busy logical CPU is `1/16 = 6.25%` in Solaris mode.
- The 30-CPU-second disposable process expired before both modes could be
  observed. This produced a useful sampling and cleanup diagnosis but did not
  complete the Irix/Solaris comparison.
- Ran `kill -TERM` after the identity check had already returned no process row,
  receiving `No such process`. The learner then correctly explained that the
  action was unnecessary; preserve the conditional identity-check habit.
- A long lab command was split after `sleep` and after `ps -o`, causing
  `sleep: missing operand`, `1: command not found`, and a missing `ps` format.
  A later `top` submission omitted the closing quote on its first physical
  line, so Bash displayed the `>` continuation prompt and accepted a real
  newline inside the quoted PID argument. The command happened to run, but
  short separate submissions remain necessary while command boundaries are
  being strengthened.
- Used `comm,$cpu` once, causing the shell to expand `$cpu` instead of passing
  the literal `ps` field `%cpu`; corrected it independently on the next command.
- After correctly calculating normalized percentages earlier, could not explain
  why the same work receives different Irix and Solaris values and guessed that
  one busy logical CPU exhausted the whole 16-CPU server. The repair established
  that the work is unchanged and only the reference whole differs.
- Initially treated `VIRT` as a nonresident pool that should decrease when pages
  enter RAM. In a later eviction example, reversed both directions by changing
  `VIRT` from `100` to `95 MiB` and `RES` from `20` to `25 MiB`. A four-page
  model repaired this to retained mappings with a smaller resident subset.
- Initially said `SHR` might not be in physical RAM and misread the two-process
  arithmetic. Repaired the model: every `SHR` page is resident, but it may be
  counted in multiple process rows and is only potentially shared according to
  the `top` field.
